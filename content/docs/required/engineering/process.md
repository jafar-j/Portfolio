# Process

## Sample

“grinvites” repository in our Github organization: all issues, branches, and pull requests.

Link: https://github.com/social-won/grinvites


## Contributions

All teammates created GitHub issues, reviewed pull requests, and maintained different branches to manage workflow. As a group we built a process that kept code organized and minimized conflicts.

## Description

Our group used a standard GitHub workflow with branches and issues to manage and distribute work. At the start of the project, each person had their own branch tied to specific issues, which kept our work separate and made it easy to track who was responsible for what. As the project progressed and the codebase became more interconnected, we combined branches and began reviewing each other's code more closely to make sure everything fit together. We held weekly group meetings where we discussed progress and assigned goals for the next session, and maintained consistent communication through a group chat. We also held smaller two-person meetings when teammates working on related components needed to discuss and integrate their work, which helped avoid conflicts and made sure things connected properly. 

Overall I think we followed through on these processes well. We had only a few merge conflicts, everyone generally knew what they were working on, and there was a lot of conversation about how different parts of the code worked together. However, we could have done a better job using GitHub's formal tools throughout. When working in person, we often identified and fixed bugs on the spot without creating GitHub issues or documenting the problems and solutions. For example, there were instances where I had my code up on a projector and we reviewed it together as a group, and instead of going through a formal pull request and code review process, we agreed I could just merge it myself since we had already looked at it together. A lot of collaboration also happened through our group chat rather than through GitHub. Therefore, if I were to do this again, I would make sure to formally document bugs and fixes more often as GitHub issues, assign them to specific people, and go through the full pull request process even when we had already reviewed code in person. It would make the project history much clearer and easier to follow.
